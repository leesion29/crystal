## 조사 기준과 확인한 원인

`docs/text_commands.md` 전체를 읽고 `macros/scripts/text.asm`, `home/text.asm`,
`engine/hangul/text.asm`, `home/name_codec.asm`, 도감·설명·라디오·이름·숫자
소비자와 대조했다. 문서는 upstream 명령 표였고, 실제 한글 글리프 높이와
호출 문맥을 추가로 확인해야 했다. 문서에는 확인한 한국어 적용 설명을 덧붙였다.
`TextCommand_SCROLL`의 border 타일이라는 설명과 실제 `(1,16)` 커서 좌표의
차이도 기록했다. 게임 출력 루틴은 변경하지 않았다.

확인한 원인은 두 가지다.

1. 기존 지침이 영문의 행·제어 개수 보존을 한국어 배치에도 강제했다.
2. `region_reference_layout.py`가 골드의 한국어 어절을 영문 페이지/행 슬롯에
   비례 배분하고 남는 행을 빈 문자열로 채웠다. 이 검사는 번역 문구나
   게임 코드 보존은 확인했지만, 의미상 문장이 끊기는 배치는 잡지 못했다.

이 경로는 사용 중단하도록 막았고 `TRANSLATION_GUIDE.md`를 수정했다.
과거 번역 JSON의 `rows`를 현재 소스에 재적용하면 안 된다. 원본 골드는
문장·문맥·변수가 일치할 때만 사용하며, 18열과 현재 변수 폭을 초과하는
골드 배치까지 무조건 복사하지 않는다.

조사 범위는 현재 diff에 국한하지 않았다. `a024806..HEAD`의 번역 이력
(`84739d6`, `1cc01a5`, `e989920`, `67c8f1c`, `ee2261a`, `b4c121b`,
`f2f6188`, `35c1181` 등)과 현재 한국어 리터럴을 함께 검색했다.
기존 그래픽·게임 로직 변경은 복원하거나 재수정하지 않았다.

스냅샷은 `.verification/text-layout-20261011/baseline/`에 있다.
후속 번역에서는 `--layout-only`로 현재 소스를 검사할 수 있다. 변수 생산자나
소비자가 바뀌면 검사기의 폭 가정도 실제 코드와 다시 대조해야 한다.

소스 보존, 12 사례, 조건 분기, 인코딩, 도감/설명 배치, 기술 이름/폰트 보존,
아이템 소스 검사, 랜드마크 소스/111 모델 사례 및 `git diff --check` 통과.
아이템·랜드마크 결과는 소스/모델 검사이며 CPU·화면 검증이 아니다.

일반·디버그의 ASM 조립은 성공했으나 **두 빌드 모두 링크 실패**했다.

```text
error: The linker script assigns section "Events" to address $66b0,
but then it would overflow ROMX by 7 bytes
at layout.link(116)
```

기존 성공 map의 `Events`는 `$25:$66b0..$7ff5`, 6,470바이트로 뱅크의 남는
공간이 10바이트였다. 이 섹션에는 `engine/overworld/scripting.asm`을 통해
`data/items/pocket_names.asm`이 포함된다. 기존 사용자 변경의 포켓 이름은
영문 45바이트에서 한국어 62바이트로 **17바이트** 커졌다. 17−10=7이
실제 진단과 일치한다. 해당 데이터와 섹션 코드는 이번에 수정하지 않았다.
섹션 이동·버퍼·ROM 구조 변경은 최신 지시에 따라 적용하지 않았다.

현재 디렉터리의 `.gbc`는 이전 성공 산출물이며 이번 교정이 반영된 ROM이 아니다.
최종 ROM 바이트/CPU 회귀 검사와 실제 화면 검사는 수행하지 않았다.
일반 SHA: `e8b96851fefce3ed6eef46f5c3a4accabd30c33a3d4da90bc1e0eaf0e9f42eaf`
디버그 SHA: `7d2268cb41c8386419b36f43d90fa2f052b8a3935e7edfe66776515378b9f733`

## 구조 변경이 필요해 보류한 문제

1. 위 `Events` 뱅크 초과: 사용자 문자열을 되돌리거나 임의로 줄이지 않았다.
2. `common_1.asm:_BenFernText1` 자동 방송: `오늘은 ` 4열 +
   `TextCommand_DAY`의 최대 `WEDNESDAY` 9열 + `(이)라는 것으로` 9열 = **22열**.
   한국어 요일 출력으로 가정하면 생기는 오탐이 아니라 현재 루틴의 실제 폭 문제다.
   `cont`/`para`를 넣으면 자동 방송이 버튼을 기다리고 진행이 바뀌므로 수정하지 않았다.
3. `common_3.asm:_SentTrophyHomeText`: `text_ram wPlayerName`은
   `PlaceRAMString`에서 일반 `PlaceString`으로 가며 packed 한글 이름 디코더를
   호출하지 않는다. 출력 폭과 별개의 이름 인코딩 경로 문제다. RAM/루틴은 유지했다.
4. 교환: `TradeAnim_GetNicknamename`은 디코딩된 종족 이름을 **11바이트**만
   복사한다. 현재 54종은 종료자 포함 13~16바이트가 필요해 종족 이름/종료자가
   잘릴 수 있다. 송신자 이름도 packed 이름을 plain `text_ram`에 넘기는 경로가
   있다. `macros/ram.asm:trademon`의 버퍼/생산자 계약 문제로 문자열 개행만으로
   해결할 수 없어 변경하지 않았다. 이름 인코딩이 정상이라는 보증 없이
   교환 화면의 동적 문자열 전체가 안전하다고 주장하지 않는다.

## 최종 게임 테스트 대상

새 ROM을 빌드할 수 있게 된 뒤 사용자가 직접 확인할 항목: `line`/`cont`의
A/B 스크롤, `para` 문단 전환, 트레이너/닉네임 최대 길이, 시간 확인의 이어쓰기,
문장 종료 후 메뉴·이벤트 진행, 라디오 자동 진행, 도감·설명·메뉴의 화면 위치.
정적 분석은 글리프 업로드·실제 프레임·PPU 잔상·버튼 체감이나 미사용 이벤트의
실행 가능성까지 보장하지 않는다. 중간 수동 테스트는 요청하지 않았다.
