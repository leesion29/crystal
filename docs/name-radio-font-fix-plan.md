# 닉네임·라디오·맵 이름·시작 메뉴 표시 수정

## 원인과 수정 계획

1. 전투 내보내기/회수 대사는 저장용 닉네임을 일반 `text_ram`으로 읽는다.
   HUD는 이름 디코더를 사용한다. 두 대사의 닉네임 출력을 기존
   `text_buffer 6`으로 연결해 같은 디코더를 사용한다. 대사 내용은 유지한다.
2. 도감 라디오는 영문용 19바이트 복사 및 40바이트 출력 버퍼를 사용한다.
   한글 escape+bank+index를 중간에서 자르고, 글리프 index를 줄 종료로
   오인할 수 있다. 단일 페이지 도감의 끝에서도 다음 데이터로 진행한다.
   완전한 글리프/행 단위로 읽고, 마지막 행 뒤에는 방송 첫 단계로 돌아간다.
   일반 라디오도 긴 한국어 문장을 수용하는 128바이트 작업 버퍼를 사용한다.
   버퍼는 라디오와 동시에 사용하지 않는 기존 적 파티 몬스터 UNION에 둔다.
   기존 WRAM/SRAM 주소는 유지하고 링크 결과로 확인한다.
3. 건물 출입 시 `LoadOverworldFont`가 한글 캐시 VRAM을 덮어쓰지만
   캐시 키를 무효화하지 않는다. 폰트 교체 전에 `ResetHangulTiles`를 호출한다.
   맵 표지 가운데 정렬도 바이트 수 대신 완성형 글리프 수로 계산한다.
4. 시작 메뉴는 메뉴를 그린 뒤 표준 폰트를 다시 올린다.
   저장 파일의 주인공 이름은 유효한 표시용 한글 문자열로 확인됐다.
   메뉴를 그리기 전에 폰트를 올려 이미 그린 이름/메뉴 타일을 덮지 않게 한다.

## 검증

- 일반/디버그 조립 및 가능하면 기존 오브젝트를 이용한 링크 검사.
- 기존 WRAM/SRAM 심볼 주소의 불변성 확인.
- 도감 설명 전체의 토큰 경계, 한 행 크기 및 끝 처리 확인.
- 사용자 재현: 한글/영문 닉네임 내보내기·교체·회수, 라디오 도감 설명의
  마지막 행, 메뉴 및 트레이너카드 왕복, 무궁시티 건물 출입 반복.
- 실제 에뮬레이터 관측을 수행하지 못한 항목은 런타임 검증 대기로 남긴다.

## 2026-10-10 검사 결과

- 변경된 main/home/ram/common 단위의 일반·디버그 조립 통과.
- 디버그 ROM은 프로젝트의 `layout.link`를 사용한 링크 통과.
  검사용 출력은 `.verification/check.gbc`, `.sym`, `.map`에 분리했고
  기존 ROM 및 세이브를 덮어쓰지 않았다.
- 기존 디버그 심볼과 WRAM/SRAM/HRAM 심볼 14,462개를 비교하여 주소 변경 0개.
- 링크된 ROM의 도감 251종, 설명 753행을 토큰 단위로 검사했다.
  최대 행 크기는 48바이트(제어 코드 포함 시 51바이트), 화면 폭은 최대 18칸이다.
  글리프 index가 `@`/`<NEXT>`/`<DEXEND>` 값과 겹치는 경우 39개를 확인했다.
  새 복사는 이 index를 제어 코드로 검사하지 않는다.
- 일반 ROM 링크는 `RAM Name Display Home` 배치 공간 부족으로 실패했다.
  이번 변경은 ROM0 코드 크기를 늘리지 않는다(home의 버퍼 주소/길이만 변경).
  일반 빌드의 기존 ROM0 여유 공간 문제는 별도 점검 대상으로 남긴다.
- 기존 `data/text/std_text.asm:155`의 unmapped `~` 경고는 변경하지 않았다.
- 에뮬레이터에서 건물 출입, 시작 메뉴 왕복, 닉네임 출력, 라디오 방송을
  직접 관측하지 않았으므로 화면상의 해결 여부는 사용자 재현 확인이 필요하다.

## 후속 재현: 기본 치코리타 이름이 `?`로 표시됨

- 사용자 확인: `?`로 표시된 개체는 닉네임을 붙이지 않은 치코리타다.
  앞선 `쁘` 사례는 브케인에게 직접 붙인 닉네임이다. 동일 입력 비교가
  아니므로 두 사례를 단순히 특정 글리프의 문제로 묶지 않는다.
- 기본 치코리타의 압축 레코드는
  `09 01 09 3A 04 3E 09 88 50 50 50`이다.
  표시용 escape 형식으로 확장하면 종료 문자 포함 13바이트다.
  기존 기본 이름 생성 경로는 확장 문자열을 11바이트만 복사하여
  마지막 글리프를 자르고 종료 문자를 잃었다. `CorrectNickErrors`는
  이 레코드를 오류로 판단하여 출력 버퍼에 `?@`를 쓴다.
- 반면 기본 브케인의 표시 문자열은 종료 문자 포함 10바이트라 이 복사에
  들어간다. 직접 입력한 `쁘`는 `05 AA` 쌍 저장 형식이며 이전
  전투 `text_ram` 경로의 쌍 미해석 문제와 구분한다.
- `CopyDefaultPokemonName`을 추가하여 고정 폭 레코드에는 Crystal 소유
  PokemonNames 표의 압축 10바이트와 종료 문자를 직접 복사한다.
  저장 레코드와 표시 버퍼의 경계를 유지하며 oldgold에 의존하지 않는다.
- 파티 생성, 박스 전송, 선물, 빈 닉네임 확정의 기본값, 부화, 진화,
  벌레잡기 대회, 야생 상대, 교환 대체 이름, 배틀타워 기본 이름 생성/
  대체 경로와 기존 파티 오류 교정의 기본 이름 복사를 연결했다.
  전화용 표시 버퍼끼리 복사는 11바이트가 아닌 STRING_BUFFER_LENGTH로 유지한다.
- 링크된 251종의 압축 이름을 검사하여 종료와 패딩이 모두 유효함을 확인했다.
  54종은 펼친 문자열이 11바이트보다 길어 기존 복사 방식에 들어가지 않는다.
  치코리타/브케인 레코드와 표시 길이를 별도로 확인했다.
- 후속 디버그 조립/링크와 diff 검사 통과. 런타임 재현은 사용자 확인 대기다.

### 다음 화면 확인

1. 새로 받은 치코리타에게 닉네임을 붙이지 않고 파티/능력치/전투 이름 확인.
2. 브케인에게 `쁘`를 입력하고 파티/능력치/내보내기/회수 이름 확인.
3. 가능하면 5글자 이름과 기본 이름의 진화·박스 왕복 확인.
4. 기존 테스트 ROM의 라디오·건물 출입 관측은 그 빌드의 결과로 기록한다.
   후속 빌드의 이름 수정 결과와 혼합하지 않는다.

이미 세이브에 잘린 기본 이름이 저장된 경우 새 생성 경로 수정만으로
그 레코드가 복원되지는 않는다. 이번 작업은 세이브를 수정하거나
개인의 닉네임을 종 이름으로 일괄 덮어쓰지 않는다. 기존 개체는
이름 감정사에서 다시 지정하거나 새 개체로 생성 경로를 검증해야 한다.
