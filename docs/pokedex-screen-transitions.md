# 도감 화면 전환과 한글 캐시

## 관찰과 재분석

사용자 관찰: 상세 화면 진입 중 약 1초간 폰트 교체가 보이고, 상세/SELECT 옵션/START 검색에서 목록으로 복귀하면 이름이 틀어진다.

문자열 저장 형식상 불가피한 현상이 아니다. 현재 목록은 BG map 0의 사이드바와 BG map 1의 이름 목록이 같은 한글 캐시를 사용한다. `TrimHangulTiles`는 현재 `wTilemap` 및 PINNED 키만 보호하며, 다른 BG 맵의 타일을 직접 조사하지 않는다.

기존 메인 초기화는 이름을 먼저 BG map 1에 올리고, `wTilemap`을 사이드바로 바꿔 문구를 그렸다. 이때 다른 맵에 남은 이름 글리프가 재사용 대상이 될 수 있었다. 이후 목록을 다시 그렸지만 새 타일 번호를 BG map 1에 전송하는 단계가 없었다. 검색 결과도 먼저 이름을 올린 뒤 다른 맵의 문구를 그렸으며, 마지막 목록 재구성에서는 이름을 다시 그리지 않았다.

최초 상세 진입은 글리프 교체 전 화면을 가리지 않았다. LCD가 켜져 있으면 한글 업로드가 프레임을 기다리므로 이전 화면의 타일 그림이 점차 바뀌는 과정이 노출될 수 있다. 이전 설명의 단순한 '화면마다 폰트를 다시 올리므로 당연하다'는 진단보다 구체적인 타일 전송·보호 순서 결함이다.

## 구현

- 메인/상세/상세 종 변경/옵션/검색/검색 결과 및 분포 복귀에서 `Pokedex_BeginScreenRedraw`를 호출한다. 검게 가린 후 표준 반전 폰트를 다시 넣어 캐시 키와 핀을 초기화하고 `wTilemap`도 비운다.
- 새 화면은 처음부터 `wHangulDynamicMode=$81`로 시작한다. 처음 한글 이전의 영어도 캐시에 넣어, 뒤의 한글이 정적 영어 타일을 덮는 혼합 경로를 방지한다.
- 메인 화면은 이름 없는 목록 맵의 속성을 준비한 뒤 사이드바를 그린다. 사이드바 한글의 기존 핀 처리를 유지한다. 이후 이름 목록을 한 번 그려 BG map 1에 전송하고 최종 팔레트를 적용한다.
- 검색 결과는 양쪽 맵에 남는 결과/타입 문구를 핀으로 보호한다. 마지막 이름 목록을 새로 그려 BG map 1에 전송한 뒤 보여준다.
- 상세 설명과 목록 이름은 텍스트 전용 단계에서 LCD를 끈 채 그린다. `_PlaceHangul`의 기존 LCD-off 업로드 경로를 사용한다. 이름 목록의 포켓몬 그림은 LCD를 다시 켠 뒤 별도로 로드한다. `Request2bpp`, `DelayFrame`, `WaitBGMap`처럼 프레임 대기를 요구하는 단계는 LCD-on에서 실행한다.
- 일반 목록 스크롤은 기존 캐시·전송 경로를 유지한다. 전환용 초기화를 스크롤마다 수행하지 않는다. 키보드·저장 데이터·이름 인코딩은 바꾸지 않는다.
- 안농 모드 진입은 기존 전용 글꼴 경로를 유지하며, 옵션 복귀 시 새 화면 초기화로 일반 반전 폰트와 캐시를 복원한다.

## 확인 범위

소스의 BG map 3/4 모드는 각각 BG map 1 타일/속성 전송이고, `WaitBGMap`은 BG map 0 타일 전송임을 확인했다. 텍스트 전용 목록 루프에는 그림 로딩과 프레임 대기가 없다. 캐시 초기화는 핀과 USED 키를 함께 지우며, 표준 폰트와 반전 상태를 일치시킨다.

빌드·실행은 사용자 담당이다. 정적 확인으로 실제 화면의 깜빡임, 시간, 모든 종 조합의 슬롯 수, 실행 중 전환 성공을 확정하지 않는다. 새 ROM에서 도감을 나갔다 다시 열어 로딩 경계를 통과한 후 검증한다.

1. 같은 목록 위치에서 상세 진입→B 복귀를 10회 반복한다. 교체 중 폰트가 노출되지 않고 이름·카운터·선택 위치가 유지되는지 확인한다.
2. SELECT 옵션→B 복귀, START 검색→B 복귀를 각각 반복한다. 목록을 한 번 스크롤한 후에도 이름과 사이드바가 유지되는지 확인한다.
3. 옵션에서 NEW/OLD/ABC 모드를 바꿔 목록과 번호·스크롤·커서를 확인한다.
4. 실제 검색 실행→검색 결과→상세→검색 결과→검색 화면→메인 순서로 돌아온다. 결과 목록 이름, 타입 문구, 모서리, 원래 메인 선택 위치가 유지되어야 한다.
5. 상세에서 위/아래로 종을 바꾸고, 분포→복귀와 울음소리를 확인한다. 설명·분류·하단 메뉴가 정상이어야 한다.
6. 안농 모드가 해금되어 있으면 진입→옵션→메인으로 복귀한다. 옵션과 목록의 글꼴을 확인한다.
7. 포획 직후 등록 화면은 별도 기존 경로이므로 기존 한글 설명과 닉네임 연결이 유지되는지 확인한다.

반복 중 누락이 남으면 화면 전환, 선택 종/모드, `wHangulDynamicMode`, 첫 깨진 행을 기록해 타일 전송 문제와 캐시 용량 문제를 구분한다.

## 검색 결과 하단 요약 재구성

사용자 화면에서 `검색 결과` 위쪽 절반이 테두리를 침범하고, 오른쪽에 `ESULTS`, `D!`가 남았다. 기존 코드가 BG 0에 한국어를 쓰고 BG 1에는 영어 문장 조각을 별도로 쓰는 구조였다. WX=$4a, SCX=5에서 BG 1 열 0은 BG 0 열 9와 맞물린다. `발견!`의 뒤쪽이 이 경계에 걸리므로 왼쪽 문구만 바꾸거나 캐시를 핀으로 보호하는 것으로는 해결되지 않는다.

하단은 동일한 전체 요약을 구성한 뒤, 목록 맵에 열 9~18과 행 11~17을 복사한다. 한글 위/아래 타일을 함께 복사하며 목록 맵의 기존 오른쪽 테두리는 복원한다. 영문 조각과 `검색 결과` 제목은 제거했다. 타입 행은 기준선 13, 개수 행은 기준선 16으로 테두리와 겹치지 않는다.

- 단일 타입: `FIRE 타입` / `22 종류 발견!`.
- 서로 다른 두 타입: `FIRE/FLYING` / 실제 개수와 `종류 발견!`. 최장 타입 두 개와 구분자는 17칸이므로 두 타입일 때는 `타입` 접미사를 생략한다. 같은 타입을 두 번 선택하면 단일 타입과 동일하다.
- 메뉴용 타입 문자열의 좌우 공백을 제거해 표시하며, 검색 조건과 검색 알고리즘은 변경하지 않는다. 조합 문자열은 기존 19바이트 `wStringBuffer3`에 최대 18바이트(종료 문자 포함)로 들어간다.

정적 확인과 실제 화면 확인을 구분한다. 빌드 및 게임 실행은 아직 사용자 확인이 필요하다. FIRE 검색, 서로 다른 두 타입 검색(가능하면 ELECTRIC/FIGHTING처럼 긴 이름), 같은 타입 두 번 선택, 결과 스크롤, 결과→상세→B 복귀에서 두 행·테두리·`견`의 위/아래가 유지되는지 확인한다.

## 검색 결과 정렬 및 구형도감 번호

추가 사용자 관찰: FIRE 타입 줄이 두 자리 개수보다 한 칸 왼쪽이며, 구형도감 번호가 이름 위에 조각으로 남는다.

수정 계획과 적용:

1. 결과 타입 시작을 열 1에서 열 2로 이동해 `22`의 첫 숫자와 맞춘다. 숫자는 기존 세 자리 우측 정렬이므로 한 자리·세 자리 개수의 첫 숫자 위치는 다를 수 있다. 두 타입의 최장 17칸도 열 2~18에 들어간다.
2. 구형도감 `Pokedex_PrintNumberIfOldMode`의 `-SCREEN_WIDTH` 이동을 제거한다. 번호를 이름 기준선에 출력하고 호출자 HL을 세 칸 전진시킨다. 열 0~2는 001~251, 열 3은 포획 표시/빈칸, 이름은 열 4부터 시작한다. 한글 위쪽 타일은 번호의 열을 건드리지 않는다.
3. 번호/정렬 데이터, 목록 높이, 스크롤과 커서 좌표, 저장 형식은 변경하지 않는다. 같은 목록 출력기를 사용하는 구형도감 검색 결과에도 적용한다. NEW/ABC는 기존 열 0 포획 표시와 열 1 이름을 유지한다.

정적 검사 대상은 251개 이름의 가로 범위 및 일곱 행의 상하 타일·번호 비중첩이다. 실제 검증은 구형도감 019 부근과 153 베이리프 부근, 스크롤, 상세→B 복귀, 구형도감 검색 결과 및 NEW/ABC 전환이다. 빌드·실행 확인 전에는 런타임 수정 완료로 판정하지 않는다.

## 가나다 정렬

기존 옵션 문구는 가나다 순이지만 `AlphabeticalPokedexOrder`는 ABRA, AERODACTYL 등 영문 이름 순이었다. OldGold와 Gold의 해당 순서표는 251개 항목과 항목 순서가 모두 동일하며, 세 프로젝트의 해당 종 상수 순서도 일치한다. 현재 이름 데이터 역시 OldGold를 사용한다.

`data/pokemon/dex_order_alpha.asm`의 순서표만 OldGold와 동일하게 교체했다. 가나다 모드 코드, 발견 여부 필터, 종 상수, 이름 데이터, 신형/구형 순서표와 저장 형식은 변경하지 않는다. 251종이 중복·누락 없이 한 번씩 등장하는지, 크리스탈 상수에 모두 대응하는지, 교체 후 항목 순서가 OldGold/Gold와 같은지 정적으로 확인한다. 표 크기는 기존과 같은 251바이트다.

빌드·게임 실행은 사용자 확인이 필요하다. 전종 발견 상태에서는 가디→강챙이→강철톤→갸라도스→거북왕으로 시작해야 한다. 일부만 발견했다면 이 순서에서 미발견 종이 빠진다. 가나다 선택 후 스크롤, 상세 진입→B 복귀, 검색 결과→복귀, 신형/구형 전환 후 가나다 재선택을 확인한다.
