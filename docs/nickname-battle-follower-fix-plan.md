# 포켓몬 닉네임: 포획 후 돈 증가 / 팔로우 이름 출력 수정 계획

작성: 2026-10-06. 갱신: 2026-10-07. 상태: N1 구현 완료, 사용자 빌드/검증 대기.

## 범위와 보호 조건

- 사용자 보고: 주인공/박스 입력 정상. 포획 후 닉네임을 지으면 돈 습득 메시지와 실제 소지금 증가. 팔로우 대사에서는 닉네임 깨짐.
- 최신 사용자 확인: 돈 습득은 닉네임 입력과 연결됨.
- 기존 번역, 영어 대사 내용, 저장된 닉네임 형식, 최대 5글자 정책은 변경하지 않는다.
- 모든 빌드와 게임 테스트는 사용자가 수행한다. 구현 단계별 사용자 검증 후 다음 단계로 진행한다.
- BGB VRAM 문제의 SCREEN_HEIGHT_PX 수정과 이번 RAM 공유/인코딩 문제를 구분한다.

## 1. 돈 증가: 코드에서 확인된 원인 경로

현재 pokecrystal.sym 기준 주소(다음 빌드에서는 재확인):

| 변수 | 주소 / 범위 | 의미 |
|---|---|---|
| wHangulNamingBuffer | $C6DF–$C6F4, 22바이트 | 한글 편집 버퍼 |
| wPayDayMoney | $C6EC–$C6EE, 3바이트 | 전투 종료 시 지급할 고양이돈받기 돈 |
| wHangulNamingBackup | $C6F5–$C70A, 22바이트 | 조합 전 편집 스냅샷 |
| wBattleParticipantsIncludingFainted | $C6FC | 위 스냅샷과 겹치는 전투 상태의 예 |

ram/wram.asm의 SECTION UNION "Miscellaneous" 안에 전투 데이터와 이름 입력 데이터가 중첩된다.
HangulNaming_Init는 wHangulNamingBuffer 22바이트를 '@'로 채운다. 이 쓰기 범위 안에
wPayDayMoney 전체가 있다. 입력 중 스냅샷도 다른 전투 상태를 덮는다.

포획 경로(engine/items/item_effects.asm)는 파티 편입과 PC 전송 모두 NamingScreen을 호출한다.
이후 ExitBattle.HandleEndOfBattle → CheckPayDay(engine/battle/core.asm)는 해당 3바이트가
0이 아니면 실제 돈을 더하고 BattleText_PlayerPickedUpPayDayMoney를 출력한다.
따라서 단순 표시 문제가 아니라 공유 RAM의 생명주기 충돌이다.
정확한 런타임 최초 쓰기와 금액은 사용자 메모리 관측으로 보강한다.

### 하지 않을 수정

- CheckPayDay 호출 삭제 / 포획이면 지급 무조건 생략.
- 이름 입력 종료 후 wPayDayMoney만 0으로 초기화.
- 편집 버퍼 초기화 삭제.

이들은 정상 고양이돈받기 보상을 없애거나 다른 전투 상태 손상을 남긴다.

## 2. 팔로우 이름: 코드에서 확인된 누락

engine/events/follower.asm의 StoreFollowerNickInBuffer는 파티 닉네임 11바이트를
wStringBuffer1로 CopyBytes만 한다. 팔로우 대사는 text_ram wStringBuffer1로 출력한다.
home/name_codec.asm의 PlaceRAMString은 wMonOrItemNameBuffer에만 특별 처리를 하므로,
여기서는 packed 닉네임이 일반 표시 문자열로 해석된다.

반면 home/pokemon.asm의 GetNickname은 복사 후 ExpandNicknameBuffer를 호출한다.
이 루틴은 저장용 2바이트 glyph pair를 표시용 escape+bank+index 문자열로 변환한다.
StoreFollowerNickInBuffer에도 동일한 명시적 변환 경계를 마련하는 것이 작은 수정이다.
일반 text_ram 전체를 packed 이름으로 해석하도록 바꾸지 않는다.

## 3. 단계별 구현 계획

### N1 — 전투 상태 보존 (최우선)

1. NamingScreen이 쓰는 공유 RAM과 포획 복귀 후 읽는 전투 변수를 대조한다.
   기존 이름 입력 변수/스프라이트 초기화도 포함하며, 새 22바이트 버퍼만 보호하지 않는다.
2. 포획 중 이름 입력에 대해 공유 작업 영역을 별도 WRAMX에 스냅샷/복원하는 경계를 설계한다.
   추천 기준은 Miscellaneous 공유 영역의 전투용 내용 보존이다. 복원 범위는 호출 중
   유지되어야 하는 상태와 의도적인 결과를 구분해 확정한다. 저장된 닉네임 결과는 복원하지 않는다.
3. 스냅샷은 NamingScreen의 첫 공유 RAM 쓰기보다 먼저 시작하고, 마지막 공유 RAM 쓰기 뒤 복원한다.
   파티 포획/PC 전송 두 호출을 모두 보호한다. 진화 등 다른 NAME_MON 호출도 분류한다.
4. 현재 map에서 WRAM0 여유는 총 20바이트이므로 큰 버퍼를 WRAM0에 추가하지 않는다.
   WRAMX bank 2에는 현재 총 $0E03 여유가 있어 후보지만, 해당 은행의 기존 사용자/인터럽트와
   배치를 검토한 뒤 전용 섹션을 쓴다. 큰 스냅샷을 스택에 올리지 않는다.
5. rSVBK 원상 복구, 호출 인자/반환 레지스터, 각 종료 경로, 비전투 이름 입력의 무영향을 확인한다.
   종전 WRAM 주소 및 저장 데이터 배치가 이동하지 않았는지 사용자의 새 sym/map로 검증한다.
6. 아래 N1 테스트가 통과한 뒤 N2로 진행한다.

N1 통과 조건:

- 같은 포획에서 닉네임 거절/입력/빈 이름 확정 모두, 고양이돈받기를 안 썼다면 돈 증가 없음.
- 1글자/5글자/삭제 후 재입력 정상, 포획한 이름과 파티 데이터 유지.
- 정상 고양이돈받기 금액이 있는 경우 닉네임 입력 전후 값과 지급 금액 유지.
- 파티가 꽉 찬 PC 전송 경로도 정상. 이 테스트가 불가능하면 검증 대기로 명시한다.
- 주인공/라이벌/박스 이름 입력 회귀 및 저장/재로드 정상.

### N2 — 팔로우 출력 변환

- StoreFollowerNickInBuffer의 복사 후 기존 ExpandNicknameBuffer 사용.
- 변환 대상은 넉넉한 표시용 wStringBuffer1뿐이다. 파티 저장 레코드에 3바이트 형식을 쓰지 않는다.
- 루틴 레지스터 계약과 현재 ROM 은행 공간을 확인한다.
- 팔로우 선택 인덱스도 정상인지 확인하되, 증거 없이 인덱스 로직은 변경하지 않는다.
- 1글자/5글자/받침/공백/기본 종 이름, 파티 순서 변경 후 서로 다른 두 이름으로 테스트.
- 대사 내용은 그대로 둔다. 파티 메뉴/팔로우/저장 재로드에서 동일 이름이어야 한다.

### N3 — 소비자 점검 (필요한 부분만)

- 포획 안내, 전투 이름, 파티 메뉴, 상태창, PC, 진화/이름 평가 등의 독립 닉네임 소비자를 목록화한다.
- packed 이름을 일반 문자열로 직접 복사/출력하는 경로를 찾고, 증상이 확인된 경계만 단계별 수정한다.
- 메일/팔로우 대사 번역이나 무관한 정리는 이번 범위에서 제외한다.

## 4. 지금 요청할 사용자 데이터

우선 동일 ROM/같은 포획 직전 상태에서 세 경우만 비교:

1. 닉네임 질문에서 아니오.
2. 예 → 글자 입력 없이 확정.
3. 예 → 한글 이름 입력 후 확정.

각 경우 돈 메시지 유무와 소지금 전후를 기록한다. 가능하면 BGB에서 wPayDayMoney
($C6EC–$C6EE)의 포획 전/입력 화면 진입 직후/확정 직후 3바이트를 보내 준다.
쓰기 중단점으로 첫 변경을 잡으면 PC와 명령도 기록한다. 기존 빌드의 데이터로도 분석 가능하므로
이 관측만을 위해 새 빌드를 요구하지 않는다.

팔로우는 파티 메뉴의 같은 이름이 정상인지, 선두를 바꾸면 현재 팔로우 이름도 바뀌는지 확인한다.
가능하면 팔로우 대사가 열린 시점의 원본 닉네임 11바이트와 wStringBuffer1($D073)의 16바이트를
관측한다. WRAMX이므로 실제 bank 1 데이터인지 확인해야 한다.

## 2026-10-07 사용자 결과와 N1 구현

- 닉네임을 설정하지 않으면 정상. 설정하면 이름과 무관하게 같은 돈 습득 메시지와 실제 돈 증가.
- 팔로우의 영어 이름은 정상, 한글 이름만 잘못된 문자로 표시. 다른 화면의 이름은 정상.
- 사용자 범위 지정: N1만 수정. 팔로우 대사는 사용자가 수정하며, 이름 변환 코드는 이번에 변경하지 않음.
- 메일 테스트는 사용자 요청으로 보류. 추후 깨비참 심부름 퀘스트에서 확인 예정이며, 검증 완료로 처리하지 않음.

구현:

- NamingScreenPreservingBattle은 이름 입력 전 wBattle부터 wBattleEnd까지의 전투 데이터를
  wCaptureNamingBattleBackup으로 복사하고, 입력이 끝나면 원래 자리로 복원한다.
- 파티 편입/PC 전송의 포획 닉네임 호출 두 곳이 이 래퍼를 사용한다.
- 전용 스냅샷은 WRAMX bank 2의 $D200에 배치한다. 현재 sym/map 기준 전투 영역은
  $C608–$C740(313바이트)이므로 스냅샷은 $D200–$D338이며 기존 bank 2 캐시/애니메이션과 겹치지 않는다.
  다음 빌드의 실제 sym/map에서 확인해야 한다.
- RAM 복사 동안만 인터럽트를 금지하고 rSVBK를 전환한 뒤 원래 은행을 복원하고 인터럽트를 켠다.
  이름 입력 루프에서는 인터럽트를 정상 사용한다.
- 파티 닉네임과 PC 전송용 wMonOrItemNameBuffer는 복원 범위 밖이므로 확정한 이름은 유지된다.
- 정상 고양이돈받기 값과 다른 전투 플래그를 보존하며, 돈 지급 코드/대사는 그대로 둔다.

다음 사용자 테스트:

1. 고양이돈받기를 사용하지 않은 포획에서 닉네임 거절/빈 이름 확정/한글 1글자/5글자 확정:
   모두 돈 습득 메시지와 돈 증가가 없어야 한다.
2. 포획한 이름과 파티 상태가 유지되고 저장/재로드도 정상인지 확인한다.
3. 가능하면 파티가 꽉 찬 PC 전송 포획에서 닉네임을 붙여 동일하게 확인한다.
4. 정상 고양이돈받기 보상의 유지 테스트는 해당 기술을 준비할 수 있을 때 확인한다.
   아직 해당 런타임 검증은 완료되지 않았다.

팔로우 대사 위치: engine/events/follower.asm의 DefaultInteraction.text.
같은 파일의 StoreFollowerNickInBuffer는 복사만 하고 변환하지 않는 상태를 유지했다.
한글 대사를 추가해도 이름의 저장 형식 변환 누락 자체는 해결되지 않으므로 테스트 결과를 별도로 기록한다.
