# TM31 이름 및 가방 복귀 글꼴 후속 수정

2026-10-10. 사용자 승인 후 구현. `create-kr-patch`의 debugging-strategy,
reinsertion, build-and-verify 및 retained-display-slots 지침에 따라
소스/최종 ROM 근거와 실제 실행 검증을 구분했다.

## 확인한 결함과 수정

- TM31의 실제 기술 ID는 MUD_SLAP(189)이다. 사용자 작업본의 이름 테이블
  189번만 `아쿠아브레이크`에서 `진흙뿌리기`로 수정했다. 다른 250개 이름은 동일하다.
- 이전 `GetName`은 13바이트를 고정 복사했다. 이전 ROM의 189번 이름은
  종료 문자 포함 22바이트였고, 실제 조립된 루틴 검사에서 복사한 13바이트에
  종료 문자가 없었다. `CopyName2`로 한글 시퀀스와 종료 문자까지 복사한다.
- 현재 최대 기술 이름은 종료 포함 22바이트다. 다섯 임시 문자열 버퍼를
  19→22바이트로 확장하고, 기술 이름 목록에 빌드 시 최대 길이 assertion을
  적용했다. 세이브 이름 레코드 상수는 바꾸지 않았다.
- TM/HM 이름 호출자는 `GetTMHMMove`의 결과인 `wTempTMHM`을
  `wNamedObjectIndex`에 명시적으로 전달한다. 목록은 이전에 이 결과 대신
  이전 `wNamedObjectIndex` 값을 읽었다. 기술 배우기/미사용 공통 경로도 동일 계약으로 맞췄다.
- 기술 배우기용 백업도 종료 문자를 포함한 22바이트로 복사한다.
  WRAM1 여유 부족 때문에 기존 미사용 24바이트 지도 임시 영역을 활용했다.
  해당 영역의 주소/크기는 유지하며, 지도 진입 시 기존대로 초기화된다.
  현재 코드에서 백업 사용 중 지도 진입 호출은 없다.
- 가방에서 취소/아이템 사용 후 전투로 복귀할 때 기본 글꼴과 한글 캐시를
  재설정하고, 메뉴 타일맵 복원 후 텍스트 상자를 비우고 HUD를 다시 그린다.
  이전 경로는 전투 추가 글꼴과 타일맵만 복원했다. 저장한 타일 번호가
  가방에서 재사용한 캐시 글리프를 계속 가리킬 수 있었으므로 이 수명 차이를 제거했다.

`GetNthString`의 원래 바이트 검색은 유지했다. 현재 기술 이름 251개 모두
한글 시퀀스 내부에 종료 바이트 `$50`이 없는 것을 검사한다.
다른 번역, TM 대응 표, 기술 효과, 키 입력/스크롤 로직은 변경하지 않았다.

## 확정하지 않은 부분

종료 문자 없는 이름의 화면 출력이 인접 메모리까지 읽을 수 있고,
가방 캐시와 저장된 전투 타일맵의 수명이 불일치하는 것은 코드로 확인했다.
그러나 사용자가 보고한 “캔슬에서 아래 키를 계속 누르면 글자 소실”의
전체 입력 흐름은 실행 재현하지 않았다. 위 두 결함이 증상의 유일한 원인인지
단정하지 않는다. 근거 없이 스크롤 또는 전역 캐시 관리 로직을 바꾸지 않았다.

## 검증 결과

- `make -j2 RGBDS=rgbds-1.0.0/ crystal crystal_debug`: 정상 종료, 후처리 완료.
- 두 ROM 모두 `tools/verify_tmhm_text.py` 통과: 실제 조립된 GetName/CopyName1
  251건, ROM bank 복귀 및 버퍼 전후 경계, TM31→189 대응, 최장 이름 백업 왕복,
  다섯 버퍼 간격, SRAM 심볼 주소 보존, 조립된 TM 이름 입력/전투 복귀 호출 순서.
- 실제 조립된 캐시 루틴으로 54개 슬롯을 채운 뒤 TM31/영문 CANCEL을
  256회 재출력하고 타일/키 대응을 검사했다. 위쪽 한글 타일 행을 남기는 조건도 포함한다.
  이는 합성된 타일맵 검사이며 실제 메뉴 입력 재현은 아니다.
- 두 ROM 모두 기존 following-sprites 278개 자료/포인터/압축/아이콘 검사,
  상태 페이지 및 전투 VRAM 복원 제한 검사, ROM 헤더/체크섬/뱅크 검사 통과.
- `git diff --check` 통과. `common_2.asm`은 작업 전 SHA256과 동일하다.
- 기존 `data/text/std_text.asm:155`의 미등록 `~` 문자 경고는 남아 있다.
- 검사기는 VRAM 업로드/하드웨어 타이밍 등을 모델링하므로 에뮬레이터 검증을
  대체하지 않는다. 사용자 최종 실행 검증 전이며 런타임 해결을 확정하지 않는다.
