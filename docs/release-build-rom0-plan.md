# 일반 빌드 ROM0 배치 복구 및 남은 작업 우선순위

## 2026-10-10 기준

사용자 일반 빌드는 `RAM Name Display Home` 배치 실패로 막힌다.
디버그 빌드와 최근 이름/전투/메뉴 표시 수정은 사용자 테스트에서 동작한다.
라디오도 후속 사용자 관측상 문제없으므로 현재 재현되는 버그로 취급하지 않는다.
이 결과는 모든 방송/경로를 전수 검증했다는 의미는 아니다.

| 우선순위 | 작업 | 근거/범위 |
| --- | --- | --- |
| P0 | 일반 빌드 복구 | 일반 ROM 자체를 생성할 수 없는 현재 확정 장애 |
| P1 | 일반 ROM 저장·재실행, 이름·전투·메뉴 회귀 | 디버그 통과 결과가 일반 ROM의 실행을 증명하지 않음 |
| P2 | 빌드 경고·미번역 및 입력 커버리지 점검 | unmapped `~` 경고가 남으며 배포 전 인코딩 누락 확인 필요 |
| P2 | 뮤뮤 에디터 Crystal 지원·속도 개선 | 사용자에 의해 뒤로 미룬 별도 도구 작업 |
| 보류 | 기절 그래픽, 글자 잘림·메뉴 배치 | 사용자가 나중에 하기로 결정; 체력바 디자인 유지 |
| 배포 전 | 옛 세이브 호환 정책·필요 시 복구 도구 | 현재 요청은 세이브 수정을 승인하지 않음 |

## 진단 및 선택할 수정

- ROM0는 고정 16KiB이며 각 섹션에는 연속 공간이 필요하다.
- 디버그 링크 map은 총 67바이트가 남지만 벡터 사이 등으로 흩어져 있다.
- 일반/디버그는 home/flag.asm의 레거시 헬퍼 포함 여부와 home/sram.asm의
  진단 코드가 달라 큰 Home 섹션의 끝 위치도 다르다.
- RAM 이름 출력 래퍼는 14바이트이다. 단순 ROM 확장은 ROM0 용량을 늘리지 않는다.
- 우선 후보는 9바이트의 독립 PlaceNicknameCommand를 별도 floating ROM0
  섹션으로 분리하는 것이다. 이 루틴 앞은 JP로 끝나며 뒤도 별도 섹션이므로
  인접 fallthrough에 의존하지 않는다. 같은 ROM0에 남아 은행 전환을 추가하지 않는다.
- 기존 루틴 삭제, 이름 기능 축소, SRAM/WRAM 배치 변경, 세이브 수정은 하지 않는다.
  후보가 배치에 실패하면 실제 map/섹션 크기를 근거로 다른 소규모 분리를 검토한다.

## 검증 계획

1. 현재 변경 소스의 일반 객체를 다시 조립해 동일 실패를 재확인한다.
2. 분리 후 일반 및 디버그 조립·layout.link 링크를 수행한다.
3. 이전/이후 디버그에서 이동 루틴의 명령 바이트와 주변 루틴 바이트를 비교한다.
4. 기존 RAM 심볼 주소가 바뀌지 않는지 검사한다.
5. 프로젝트 RGBFIX 및 stadium 후처리까지 적용한 검사용 ROM을 별도 경로에 만든다.
6. 실제 부팅·저장·종료·재실행과 닉네임/USER/TARGET 대사는 사용자 실행 확인을 요청한다.
   빌드 통과를 런타임 통과나 옛 세이브 호환 증명으로 바꾸어 말하지 않는다.

## 수정 및 검증 결과

- 수정 전 일반 객체로 동일 링크 실패를 재현했다. 원인은 ROM0 총량 초과가 아니라
  연속 공간 부족이었다. 일반 Home 섹션은 디버그보다 7바이트 커 배치가 달랐다.
- `home/name_codec.asm`의 9바이트 `PlaceNicknameCommand`에 독립 ROM0 섹션을
  부여했다. 명령은 추가·삭제·변경하지 않았다.
- 수정 후 일반 ROM에서 14바이트 `PlaceRAMString`은 `$00f1`에,
  9바이트 `PlaceNicknameCommand`는 `$3ff5`에 배치됐다. ROM0 잔여 총량은 60바이트다.
  공간 여유 자체가 늘어난 것은 아니므로 후속 ROM0 코드 추가 시 다시 주의해야 한다.
- 기존 생성 그래픽을 사용해 일반·디버그 각각 18개 객체를 모두 재조립하고
  `layout.link` 링크, RGBFIX, stadium 후처리를 통과했다.
  그래픽을 포함한 완전한 clean make를 수행한 결과는 아니다.
- 이전/이후 디버그 ROM에서 `PlaceNicknameCommand` 9바이트,
  `PlacePlayerName` 119바이트, `CopyName1` 23바이트,
  `PlaceRAMString` 14바이트가 각각 동일했다. 래퍼의 명령 경계와 호출/점프 대상도 확인했다.
- 기존 RAM 심볼 14,464개를 비교했으며 주소 변경은 0개다.
  이것만으로 옛 세이브의 모든 호환성을 증명하지는 않는다.
- 일반 검사용 ROM은 `.verification/release-rom0.gbc` (2MiB),
  디버그는 `.verification/debug-rom0.gbc` (4MiB)에 생성했다.
  두 ROM의 헤더·전체 체크섬을 별도로 검사해 통과했다.
  기존 배포 ROM과 세이브는 덮어쓰지 않았다.
- `data/text/std_text.asm:155`의 unmapped `~` 경고는 남아 있다.
  이번 배치 실패와 별개이며 임의로 대사 내용을 바꾸지 않았다.

## 다음 실행 확인 (P1)

1. 일반 빌드 ROM을 부팅하고 기본 이름과 한글 닉네임이 정상 표시되는지 확인한다.
2. 야생 출현 → 공격 → 쓰러뜨림/포획에서 적 이름이 정상인지 확인한다.
3. 기술 선택 → 가방/포켓몬 화면 → 기술 선택 복귀 시 빈 기술 `-`가 유지되는지 확인한다.
4. 건물 진입/퇴장 후 지역 이름과 주인공 메뉴 이름을 확인한다.
5. 테스트용 세이브에 저장한 뒤 에뮬레이터를 완전히 종료하고 다시 실행해
   이름과 파티 상태를 확인한다. 기존 중요한 세이브는 별도 백업한다.

실행 확인은 아직 완료로 처리하지 않는다. P0 빌드 복구는 완료했고,
이제 위 일반 ROM 회귀 확인을 우선한다.
