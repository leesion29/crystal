# 주인공 한글 이름 입력: 재설계 및 단계별 검증

## 목표와 범위 (2026-10-05 재설정)

- 현재 구현·검증 범위는 새 게임의 주인공 이름 입력이다.
- 최종 입력 구성은 참조 골드 한글판처럼 자음과 모음을 한 화면에 표시하고,
  영문 입력·영문 전환 없이 정정/결정으로 편집·확정하는 방식이다.
- 한글 이름 최대 5글자를 지원한다. 입력·조합·확정·재표시·저장까지 이어져야 한다.
- 통짜 키보드 그래픽은 gold/gfx/naming_screen/hangul.png 및
  gold/data/text/name_input_chars.asm을 기준으로 한다.
- 박스·메일·포켓몬 별명·라이벌 입력의 실제 검증은 보류한다.
  공통 루틴의 변경이 이 경로에도 영향을 줄 경우 미검증임을 기록한다.
- 화면 미관과 최종 키보드 배치는 기능이 안정된 뒤 정리한다.
- 대사·번역은 사용자 승인 없이 변경하지 않는다. Crystal에 jmp를 추가하지 않는다.
- 모든 빌드 및 게임/BGB 실행은 사용자가 한다. 에이전트는 소스·기존 산출물
  정적 분석과 수정만 수행한다. 소스 검사 결과와 게임 실행 결과를 구별한다.

## 현재 관찰과 기준 산출물

사용자 보고:
- 단자음·단모음·기호 입력, 가와 같은 초성+중성 조합은 동작한다.
- 현재 한글 입력 한도는 2글자다.
- 종성·겹받침·받침 이동은 검증이 충분하지 않다.
- 공백처럼 보이는 셀을 고르면 숫자가 입력된다.
- ABC 전환 시 크래시한다. 보고된 PC는 $7644, 초기화 진단값은 $04다.
- 초기 진입은 현재 동작한다. 프리징 해결 또는 조합 전체 완성을 선언하지 않는다.

정적 분석 기준:
- 작업공간의 pokecrystal.gbc SHA256:
  684C475B375DEF78CE122125BBB37EE211DCC65B0BFA0FFAC37D0DEE44E29D22
- 함께 놓인 sym: naming 화면 bank $21, 조합 코드 bank $75.
- 이 ROM의 $21:$7644는 HangulNaming_KeyTile.blank의 ld a,$7f 명령의
  피연산자 바이트다. $10:$7644는 Cleffa 데이터다.
- 따라서 PC $7644만으로 현재 실패 명령/실행 뱅크/원인을 확정할 수 없다.
  BGB에서 실제 선택 bank와 읽힌 opcode, SP를 확인해야 한다.
- 진입 완료 후 코드가 기록하는 초기화 값은 $07이다. 화면을 열고 조작하다가
  $04가 보고된 이유도 미확정이다. 이전 ROM 세이브스테이트, 실행 ROM 불일치,
  진단값 덮어쓰기 가능성을 관찰로 구분한다.

## 코드 분석: 확인된 문제와 남은 가설

### A. 페이지 전환에 남은 뱅크 호출 결함

HangulNaming_SwitchPage는 2(자음),3(모음),0(영문 대문자),1(영문 소문자)를
순환한다. 영문 페이지 렌더링의 비알파벳 문자는
NamingScreen_ApplyTextInputMode.cached_tile로 가서 homecall _PlaceHangul을 호출한다.

homecall 매크로는 호출 지점에서 ROM bank를 바꾸고 이어서 call을 실행한다.
이 매크로를 ROM0에서 쓰면 호출 코드가 계속 존재하지만, 현재 호출 지점은
교체되는 ROMX bank $21이다. 뱅크 변경 직후에는 다음 명령조차 다른 bank에서
읽히게 된다. 이는 정적 코드에서 확인된 호출 방식의 결함이다.

다만 이번 사용자 크래시가 이 경로인지 아직 런타임 관찰로 확인하지 않았다.
먼저 전환/호출 전후 진단값과 bank를 수집한다. 이후 원작에 없는 영문 전환을
주인공 입력에서 제거하는 단계로 진행한다. 다른 입력 화면까지 같은 변경을
적용한 것으로 간주하지 않는다.

이전 원인 설명의 정정:
- Get1bpp는 LCD-on일 때 Request1bpp를 사용한다. LCD가 켜져 있다는 사실만으로
  이 함수가 위험하거나 크래시 원인이라고 할 수 없다.
- 동적 출력 제거 후 초기 진입이 동작한 관찰은 유효하지만, 정확한 원인 확정과
  모든 페이지 전환의 회귀 검증을 의미하지 않는다.

### B. 숫자 셀의 표시/입력 불일치

HangulNaming_KeyTile은 $a0 이상을 먼저 자모 구간으로 보내고,
$d5 이상이면 blank로 보낸다. 따라서 $f6-$ff 숫자 코드가 .special의
숫자 분기에 도달할 수 없다. 입력 테이블에는 그대로 숫자 코드가 남아 있으므로
빈 모양의 셀에서 숫자가 입력되는 현상이 설명된다.

다음 셀 검증 단계에서 표시와 논리 입력을 함께 바로잡는다.
원작 최종 배치에서 유지할 숫자·기호 범위는 골드 실제 활성 셀 기준으로 확인한다.
0으로 지정된 비활성 셀과 $7f의 실제 공백 입력 셀을 구별한다.

### C. 명령 라벨의 타일 소유권 충돌

고정 명령 알파벳 $5c-$75는 NAMINGSCREEN_BORDER=$60과 겹친다.
초기화에서 명령 폰트를 먼저 적재하고 border를 나중에 쓰므로 E 타일이
테두리로 덮인다. DEL/END의 깨진 모양과 일치하는 정적 결함이다.
최종 정정/결정 그래픽 배치 시 골드의 전용 타일과 보호 범위를 표로 명시한다.

### D. 2글자 한도와 5글자 저장 설계

입력기의 현재 한도: PLAYER_NAME_LENGTH-1 = 7바이트.
실제 wPlayerName 레코드: NAME_LENGTH = 11바이트.
현재 직렬화는 한글마다 $17,bank,index 3바이트를 기록한다.
따라서 입력기 한도를 15로 올리는 것만으로는 실제 레코드에 들어가지 않는다.

우선 검토할 구조는 골드의 2바이트 글리프 ID를 주인공 이름 레코드에 사용하고,
화면·대사 삽입 시 Crystal의 $17,bank,index 출력 형식으로 변환하는 방식이다.
5*2+종료 1 = 11바이트이므로 레코드 폭을 유지할 수 있다.

이 구조는 아직 구현 결정/검증이 끝나지 않았다. 구현 전 아래를 확인한다.
- 기본 후보 이름 및 기존 1/3바이트 이름과의 구별 규칙, 종료 및 패딩 규칙.
- 이름 입력 중 임시 조합/편집 표시와 확정 저장의 차이.
- NamePlayer, InitName, CopyName1/2, 대사 버퍼 삽입, 메뉴·트레이너 카드.
- 주인공 이름을 OT로 복사하는 경로, 이름 비교, 레포트 저장과 재로드.
- 기존 저장 데이터 처리 및 중간 표시 버퍼 용량.
이 소비자 목록이 확정되기 전에는 저장 형식이나 전역 이름 상수를 바꾸지 않는다.
단순히 이름 입력 화면에 5글자가 보인 것을 저장 지원 완료로 취급하지 않는다.

### E. 조합 검증

조합 코드는 골드의 2바이트 편집 버퍼와 자모 테이블을 사용한다.
테이블의 $4000 배치 assertion은 유지한다. 가 입력 성공은 사용자 확인 사실이다.
각/겹받침/받침 이동/삭제/확정 조건은 각각 별도 테스트 대상으로 남는다.
임시 자모를 입력할 수 있다는 사실과 미완성 이름 확정 허용 여부를 혼동하지 않는다.

| --- | --- | --- |
| A0 | 주인공 페이지 전환에 진단값만 추가 | 현재 크래시를 재현해 bank, PC, SP, 단계, 페이지를 확보 |
| A1 | 주인공에서 영문 전환 제거, 자음/모음 접근 유지 | A/SELECT 전환 반복 및 가 입력이 안정적이면 진행 |
| B | 셀 입력 코드와 표시 대응, 비활성 셀 처리 | 숫자 셀·공백 셀·비활성 셀의 결과가 각각 정의와 일치 |
| C | 종성·겹받침·받침 이동·단계별 삭제 및 확정 | 각/가가/닭과 B 역순 삭제, 빈 이름/미완성 확정 결과 확인 |

한 번에 조합/저장/타일 배치를 함께 바꾸지 않는다.

## A0 진단 수정과 첫 테스트

이번 소스 변경은 NAME_PLAYER 페이지 전환과 영문 glyph 호출 경로에
아래 진단값을 추가하는 것으로 제한한다. 키 테이블·조합·저장 한도는 유지한다.
기존 wHangulNamingInitStage를 사용하므로 새로운 WRAM 필드/주소 이동이 없다.

| 값 | 마지막으로 기록한 위치 |
| --- | --- |
| $01-$07 | 기존 초기화 단계 (진입 완료는 $07) |
| $80 | 주인공 페이지 전환 시작 |
| $81 | 다음 페이지 번호 기록 완료 |
| $82 | 영문 페이지 렌더링 진입 직전 |
| $83 | 영문 glyph의 homecall _PlaceHangul 직전 |
| $84 | 그 homecall에서 복귀 |
| $85 | 자음/모음 페이지 렌더링 진입 직전 |
| $86 | 전환 렌더링에서 복귀 |

사용자 실행 순서:
1. 새 빌드를 BGB에서 다시 로드하고, 다른 빌드의 세이브스테이트를 사용하지 않은
   새 게임에서 주인공 이름 입력에 진입한다.
2. 버튼을 누르기 전 wHangulNamingInitStage가 $07인지 확인한다.
3. ABC 또는 SELECT로 자음 → 모음 → 다음 페이지를 선택한다.
4. 멈추면 PC뿐 아니라 BGB의 실제 실행 bank:PC, hROMBank, SP,
   wNamingScreenLetterCase, wHangulNamingInitStage를 기록한다.
5. $83에서 다른 ROM bank의 코드로 실행이 넘어가면 homecall 가설을 확인하는
   근거가 된다. $04가 그대로라면 실행 ROM·심볼·초기화 경로부터 재대조한다.

현재 sym 기준 값 (새 빌드 sym이 우선):
- hROMBank: $FF9D
- wNamingScreenLetterCase: $CF64
- wHangulNamingInitStage: $C70D

디버거에서는 새 ROM과 같은 빌드의 sym을 사용한다. 이전 PC 번호를 새 소스의
같은 위치라고 가정하지 않는다. A0 소스 정적 확인은 런타임 크래시 원인 확정이나
수정 완료를 의미하지 않는다.

## A0 결과 및 A1 수정

사용자 BGB 결과:
- 진입 직후 초기화 단계 $07. 초기화 완료까지 도달한 것이 확인되었다.
- 전환 중 크래시: PC=$CF6C, SP=$BFE8, hROMBank=$01,
  wNamingScreenLetterCase=$00, wHangulNamingInitStage=$83.

해석:
- $00은 자음 페이지가 아니라 내부 영문 대문자 페이지 번호다. 화면의 모양과
  실제 페이지 상태를 구별해야 한다.
- $83은 ROMX의 homecall _PlaceHangul 직전이다. 복귀 후 $84는 기록되지 않았다.
  PC는 코드가 있는 ROM을 벗어나 WRAM에 있고 SP도 비정상 영역으로 벗어났다.
  이는 앞서 확인한 ROMX 호출 지점의 뱅크 변경 결함을 강하게 뒷받침한다.
- $FF9D=$01은 크래시 시점의 소프트웨어 bank 기록이다. 뱅크 변경 직후의 실제
  첫 명령까지 추적한 것은 아니므로 그 이후의 잘못된 명령열은 확정하지 않는다.

A1 변경:
- NAME_PLAYER만 자음($02) ↔ 모음($03)으로 전환한다.
- ABC 버튼과 SELECT가 공유하는 전환 함수에서 영문 페이지 $00/$01 진입을 제거한다.
- 다른 이름 입력 유형의 기존 페이지 전환, 키 테이블, 조합, 저장 한도는 유지한다.
- ABC라는 임시 라벨은 그대로다. 최종 한 화면 키보드와 정정/결정 라벨은 E단계다.
- 진단값은 유지한다. 성공적인 전환 후에는 $86이 기록되어야 한다.

A1 사용자 테스트:
1. 새 ROM/동일 빌드 sym으로 새 게임에서 주인공 이름 입력을 연다.
2. ABC를 10회, SELECT를 10회 전환한다. $CF64는 $02/$03만 반복해야 한다.
3. 전환 종료 때 $C70D=$86인지 확인한다.
4. ㄱ → 모음 페이지의 ㅏ로 가를 입력하고 B로 지운 뒤 다시 입력한다.
5. 이 단계에서는 한도 2글자, 빈 셀의 숫자 입력, 그래픽 문제는 기존 상태로 남는다.
6. 멈추면 PC, SP, $FF9D, $CF64, $C70D를 다시 수집한다.

정적 검사 완료, 빌드/게임 실행 미실행. A1 해결 여부는 위 사용자 테스트 대기다.

## A1 사용자 검증 통과 및 B 수정

사용자 결과:
- ABC와 SELECT 각각 10회 전환: 정지 없음.
- 페이지 번호 $02/$03 반복, 전환 후 단계 $86 확인.
- 가 입력 → B 삭제 → 가 재입력 정상.
- 추가로 각청의 연속 조합 및 출력 정상. 종성 조합의 일부 경로에 대한 통과
  근거이며, 겹받침·받침 이동·역순 삭제 전체의 검증을 뜻하지 않는다.

B 단계에서 정정한 그래픽 해석:
- gold/gfx/naming_screen/hangul.png의 $35-$3e는 숫자 0-9가 아니라
  골드의 결정 라벨 조각이다. 픽셀과 골드 NameInputLayout의 소비 위치로 확인했다.
- 기존 KeyTile의 숫자 분기 결함은 존재하지만 이를 $35-$3e로 연결해도 숫자가

## C 사용자 검증 통과 / D0 저장 설계

사용자가 첨부한 결과에서 C의 종성 삭제, 겹받침 삭제, 받침 이동, 전용 복합모음,
초과 입력 거절 및 복원, 정상 확정 후 재표시가 모두 통과했다.
이는 표에 지정한 대표 경로의 실행 증거다. 모든 음절, 미완성/빈 이름 확정 정책,
저장 후 재실행까지 검증된 것은 아니다. 이번 D0에서는 실행 코드를 변경하지 않는다.

### 저장 방식과 경계

- NAME_LENGTH=11 및 WRAM/SRAM 레코드 배치를 유지한다. PLAYER_NAME_LENGTH나
  NAME_LENGTH를 전역 확대하지 않는다. 현재 3바이트 한글 5개+종료는 16바이트라
  wPlayerName 뒤의 wMomsName을 침범한다.
- 새 주인공 이름의 저장 형식은 골드 글리프 ID 두 바이트씩, 최대 5개,
  그 뒤 '@'($50)로 한다. 사용하지 않는 레코드 바이트도 '@'로 채운다.
  자모·음절·기호·공백 모두 편집 버퍼의 동일한 2바이트 ID로 저장한다.
- 새 레코드는 모든 글자가 bank=$01-$0b인 쌍이다. index=$50도 유효한 페이로드이므로
  종료 검사는 반드시 쌍의 시작에서만 한다. 최대 10바이트 후 종료가 있어야 한다.
  5번째 글자의 조합은 허용하되 6번째 글자가 생기는 받침 이동도 스냅샷 복원한다.
- 편집 버퍼는 기존 골드식 2바이트 상태를 유지한다. 표시 시에만 현재 Crystal의
  $17,bank,index 문자열로 확장한다. 확정 레코드와 표시 문자열을 혼동하지 않는다.
- STRING_BUFFER_LENGTH=19인 wStringBuffer1~5는 최대 16바이트 표시 문자열을
  담을 수 있다. 반면 wMonOrItemNameBuffer, OT 및 NAME_LENGTH 버퍼는 11바이트다.
  모든 CopyName 호출을 무조건 확장하는 방식은 금지한다.
- 변환 버퍼는 호출별 소유권/중첩 호출을 정하고 사용한다. 단지 19바이트라는 이유로
  이미 사용 중인 wStringBuffer를 덮어쓰지 않는다. 전용 임시 버퍼를 선택한다면
  WRAM 배치와 수명부터 확인한다.

### 기존 이름과 구별 / 손상 방지

이름 레코드를 받는 전용 디코더에서만 형식을 구별한다. 일반 PlaceString에
저범위 바이트를 무조건 한글 bank로 해석하는 분기를 넣지 않는다.
기존 텍스트의 일본어 문자·제어값과 충돌할 수 있기 때문이다.

- 첫 바이트 $01-$0b: 전체 레코드를 쌍 형식으로 검증한 뒤 확장한다.
- 첫 바이트 $17 또는 기존 일반 문자: 기존 3/1바이트 이름으로 검증·표시한다.
- 첫 바이트 '@': 빈 이름이다. 현재 후보/기본 이름 처리 정책을 유지한다.
- 이 구별은 현재 영문 기반 Crystal의 일반 문자 및 $17 이름을 대상으로 한다.
  일본어 저범위 문자로 시작하는 외부 이름까지 호환된다고 주장하지 않는다.
- 11바이트 경계, bank 범위, 종료 위치, 패딩을 검증한다. 잘못된 입력의 처리 방식은
  기존 오류 처리와 대조해 결정하며, 정상 이름을 다른 글자로 조용히 치환하지 않는다.
- 기존 후보 이름·기존 저장 이름을 모두 즉시 재인코딩하지 않는다. 기존 이름의
  읽기와 새 이름의 쓰기를 분리한다. 같은 폭이라는 사실만으로 세이브 호환을
  선언하지 않는다. 기존 이름/OT 비교가 필요한 경우 비교용 정규화도 검토한다.

### D1을 다시 나누는 구현 순서

   표시용 문자열, 확정 시에는 11바이트 쌍 레코드를 쓴다. NAME_PLAYER만 5글자로

3. **D2a: 주인공 레코드의 나머지 소비자.** 메뉴/카드/OT 복사·표시·검증·비교를

4. **D2b: 저장과 재실행.** 새 이름으로 레포트 후 종료하고 새 실행에서 로드한다.

기존 세이브/OT/통신 호환이 구현·검증된 상태가 아니다. 이번에는 계획서만 수정했고,
빌드와 게임 실행은 수행하지 않았다.

## D1a 구현: 이름 읽기/표시 경계 (사용자 실행 검증 대기)

이번 변경은 새 저장 형식을 쓰기 전에 읽는 경로를 마련하는 단계다.
현재 이름 입력 한도 2글자, 입력 중/확정 시의 $17 직렬화, 조합/삭제 코드,
대사/번역 문자열, WRAM/SRAM 배치는 변경하지 않았다.

구현 파일과 계약:

- engine/hangul/name_codec.asm의 DecodeHangulName은 11바이트 이름 레코드를
  먼저 검증한 뒤 최대 16바이트 Crystal 표시 문자열로 변환한다.
  첫 바이트가 $01-$0b이면 골드식 쌍, 아니면 기존 일반 문자/$17 형식을 판독한다.
  bank/index/종료 경계를 검사하며, 쌍 이름은 종료 뒤 '@' 패딩도 검사한다.
  기존 이름은 현재 writer가 패딩을 갱신하지 않으므로 종료 뒤 바이트를 무시한다.
- index=$50 및 index=$17을 종료/escape로 오인하지 않도록 페이로드를 건너뛴다.
  손상 레코드는 carry set, B=$ff로 실패한다. 실패 시 출력 버퍼/원본은 그대로다.
  정상 이름을 임의 문자로 치환하거나 레코드를 자동 수정하지 않는다.
- home/name_codec.asm의 PlacePlayerName/PlaceHangulName은 ROM0에서 안전하게
  디코더를 호출하고, 호출별 스택 임시 버퍼에 문자열을 만든 뒤 PlaceString을 쓴다.
  16바이트 임시 버퍼와 저장한 HL을 복귀 전에 회수한다. 정상 복귀의 HL/BC는
  기존 PlaceString과 같은 시작/종료 좌표 계약이다. 실패 시 출력하지 않으며
  carry set, BC=원래 HL로 복귀한다.
- homecall은 복귀 때 호출 전 AF를 복원하므로 디코더의 carry가 보존되지 않는다.
  wrapper는 별도 B=$ff 실패 상태를 확인한다. ROMX에서 homecall을 쓰지 않는다.
- 공통 문자열 버퍼를 빌리지 않고 WRAM0 스택을 사용하므로 기존 변수 주소는 유지된다.
  WRAM0 스택은 256바이트이며 이번 임시 표시 공간은 16바이트다. 실제 통합 호출의
  스택 여유와 인터럽트/출력 동작은 게임 검증 대상이지 모델 검사만으로 확정하지 않는다.
- 기존 map에서 ROM0의 여유 대부분은 헤더 아래의 작은 빈 영역에 있었다.
  wrapper를 독립 ROM0 섹션에 두어 거의 찬 Home 섹션을 불필요하게 늘리지 않았다.
  실제 새 섹션 배치/분기/뱅크는 사용자 빌드 산출물에서 확인해야 한다.
- 연결한 소비자는 home/text의 <PLAYER>/<PLAY_G> 이름 삽입과 트레이너 카드 이름이다.
  일반 PlaceString/TextCommand_RAM, CopyName1/2, 다른 이름 및 OT 독자는 그대로다.
  따라서 아직 새 쌍 이름을 게임 전체에 저장하지 않는다. 다른 직접 출력 경로는 D2에 남는다.

에이전트 정적 확인:

- 소스 명령 모델에서 14,334개 레코드 사례를 확인했다. bank=$01-$0b,
  index=$00-$ff가 마지막 글자에 오는 1~5글자 쌍 이름, 10바이트 일반 이름,
  페이로드 $50/$17, 종료 누락/잘림/잘못된 bank/패딩을 포함한다.
  경계 밖 원본 읽기, 출력 버퍼 쓰기, 원본 변경 및 실패 시 부분 출력을 검사했다.
- wrapper 모델 6개 사례로 기존/쌍/손상 이름과 호출 전 carry의 두 상태에서
  HL/SP 복귀, BC 종료 좌표, homecall의 AF 복원 처리 및 실패 시 출력 미호출을 확인했다.
  렌더러/뱅크 호출의 효과를 모사한 것이며 실제 렌더러를 실행한 검사가 아니다.
- 디코더의 소스상 상대 분기 거리를 확인했고 git diff --check도 통과했다.
- 위 모델은 소스 로직 확인이다. 조립된 SM83 명령, 최종 링크 배치, 인터럽트,
  에뮬레이터 동작이나 5글자 기능 완료의 증거로 취급하지 않는다.
  에이전트는 빌드/실제 게임 테스트를 수행하지 않았다.

D1a 사용자 테스트:

1. 새 빌드로 새 게임에서 각청을 입력한다. 페이지 전환, B 삭제/재입력 후 확정하고
   바로 다음 이름 포함 대사에서 각청이 정상적으로 나오는지 확인한다.
   대사 자체와 이름 뒤 글자/기호가 빠지거나 위치가 밀리지 않아야 한다.
2. 기존 이름 후보 중 하나를 선택해 다음 이름 포함 대사를 확인한다.
   후보 문자열을 다시 번역/수정하지 않아도 기존처럼 표시되어야 한다.
3. 스타트 메뉴에서 트레이너 카드를 열어 이름과 나머지 항목이 정상이고 닫을 수
   있는지 확인한다. 기존 세이브가 있다면 그 짧은 이름의 카드도 확인한다.
4. 이 단계에서는 입력 한도가 여전히 2글자다. 쌍 형식의 실제 게임 출력은 D1b에서
   새 writer가 연결된 뒤 별도로 검증하며 모델 통과만으로 실행 통과라고 기록하지 않는다.

실패하면 발생 경로, 보이는 이름/뒤쪽 대사, PC/SP/hROMBank와 같은 빌드 sym을
제공한다. 이름만 사라지는 경우 wPlayerName의 11바이트도 확보한다.
필요하면 PlaceHangulName.invalid 또는 DecodeHangulName.invalid에 breakpoint를
걸어 형식 판독 실패와 출력/복귀 문제를 구분한다. 심볼 주소는 새 빌드 sym이 우선이다.
D1a 통과 뒤에만 D1b의 5글자 쓰기/편집 표시 분리를 진행한다.

## D1b 구현: 주인공 5글자 편집 및 확정 저장

사용자가 D1b 진행을 요청하여 구현했다. D1a 개별 실행 결과는 별도로 제공되지
않았으므로 기존 후보/이름 출력 회귀를 이번 실행 검사에 포함한다.

변경 범위:

- NAME_PLAYER만 공개 입력 한도를 5글자로 설정한다. 다른 입력 유형의 한도,
  저장 형식, 대사/번역 문자열 및 WRAM/SRAM 배치는 변경하지 않는다.
- 주인공 입력 중에는 wHangulNamingBuffer의 골드식 쌍 상태만 갱신한다.
  기존 목적지 wPlayerName에는 확정 전까지 쓰지 않는다.
  wNamingScreenCurNameLength는 이 경로에서 논리 글자 수(0~5)가 된다.
  wHangulNamingCurNameLength는 계속 편집 바이트 수(0,2,...,10)다.
- 각 입력의 조합은 기존 골드 코드에 맡긴다. private max=20 및 22바이트
  스냅샷은 유지해 임시 조합을 허용한 뒤 10바이트 초과 결과를 전부 복원한다.
  단순 6번째 자음뿐 아니라 마지막 받침이 이동해 6번째 글자를 만드는 경우도
  같은 경계에서 거절한다. 실제 골드 조합 실행은 별도 테스트 대상이다.
- 주인공용 Serialize는 표시 전 편집 버퍼의 사용하지 않는 부분을 11바이트
  경계까지 '@'로 정리한다. 이름 화면은 PlaceHangulName으로 이 버퍼를 표시한다.
  별도의 16바이트 문자열을 wPlayerName에 기록하지 않는다.
- HangulNaming_CommitPlayer는 편집 길이의 짝수/최대 10바이트 및 각 bank를
  검증한 뒤에만 목적지 11바이트를 '@'로 채우고 사용한 쌍을 복사한다.
  index=$50/$17도 데이터 그대로 저장된다. 손상 상태에서는 목적지를 변경하지
  않고 carry set으로 거절하며 END는 화면을 종료하지 않는다.
- 빈 이름은 전부 '@'로 확정하고 기존 intro InitName의 기본 이름 처리를 유지한다.
  자모/공백 이름에 대한 새 확정 제한이나 새 대사는 추가하지 않았다.
- StoreEntry의 정상 경로들은 carry clear를 반환한다. 이를 이용해 주인공의
  실패한 확정만 입력 화면 종료를 막는다. 메일/다른 입력의 실제 회귀는 미검증이다.
- SavePlayerData/LoadPlayerData는 기존대로 wPlayerData 전체를 바이트 복사한다.
  새 11바이트 이름도 그 영역에 포함되므로 레코드 폭이나 저장 배치를 바꾸지 않는다.
  이것은 저장/재로드 통합 동작이 검증되었다는 뜻이 아니다.

소스 검사 결과:

- 소스 명령 모델 14,103개 사례로 확정 쓰기/경계, 잘못된 길이·bank의 쓰기 거절,
  편집 중 목적지 불변, 0~5글자 표시 패딩, 6번째 추가/받침 이동 결과 복원,
  5번째 자리 내부 변경 허용, 다른 이름의 기존 3바이트 직렬화를 확인했다.
- 모든 bank=$01-$0b 및 index=$00-$ff가 마지막 자리에 오는 1~5글자 저장 사례를
  포함했다. CopyBytes/ByteFill와 골드 조합 결과는 모델의 호출 효과로 제공했다.
  조립된 명령이나 골드 조합 코드 자체를 실행한 검증으로 취급하지 않는다.
- 어댑터 소스의 상대 분기 거리와 git diff --check를 확인했다.
  에이전트는 빌드/게임 실행을 수행하지 않았다. 실제 bank/분기/스택 동작은
  사용자의 새 빌드 및 실행 결과로 확인해야 한다.

D1b 사용자 테스트 (항목 사이에는 이름을 비우거나 새 게임으로 다시 진입):

1. 가나다라마 5글자를 입력한다. 6번째 ㄴ과 ?/!를 선택해도 기존 이름과 입력
   커서가 변하지 않아야 한다. ABC/SELECT 전환으로 이름이 변하면 안 된다.
2. 가나다라가에서 ㄱ을 추가해 가나다라각으로 만든다. 이어 ㅏ를 누르면 받침
   이동으로 6번째 글자가 생기므로 거절되고 가나다라각이 유지되어야 한다.
   B 한 번은 가나다라가, ㄱ 재입력은 가나다라각이어야 한다.
3. B로 마지막 글자를 단계별 삭제하고 다른 글자를 재입력한다. 마지막 글자 삭제
   후 그 글자/윗부분 잔상이 남거나 커서가 이전 위치에 고정되지 않아야 한다.
4. 가나다라각을 START → A로 확정한다. 다음 이름 포함 대사와 트레이너 카드에서
   5글자가 유지되고 이름 뒤 문장/기호, 카드의 다른 항목 및 닫기가 정상이어야 한다.
5. 기존 후보 이름 선택 후 대사/카드 표시도 확인한다. 빈 이름 확정 시 기존의
   기본 이름 처리로 돌아가는지 확인하되 새 정책/문구 변경을 기대하지 않는다.

필요할 때만 BGB 메모리 확인 (최신 sym 기준):

- 5글자 입력 중: wHangulNamingCurNameLength=$0a,
  wNamingScreenCurNameLength=$05, wNamingScreenMaxNameLength=$05.
- 확정 후 가나다라각의 wPlayerName 11바이트:
  `01 01 02 3a 02 d9 03 c3 01 02 50`.
- wMomsName은 확정 직전과 직후 동일해야 한다. 아직 입력 중인 wPlayerName은
  편집 버퍼와 같을 필요가 없다(확정 전 목적지를 보존하는 설계다).
- 크래시는 PC/SP/hROMBank, 이름 누락은 wPlayerName 11바이트 및 발생 화면을
  먼저 기록한다. 이름 입력 중 실패라면 편집 버퍼 첫 11바이트/길이도 확보한다.

이번 빌드는 D1b 입력·확정·직접 재표시 검증용이다. OT 검증/비교, 일부 버퍼
전달·다른 직접 출력은 D2에서 보완해야 하므로 게임 전체의 5글자 이름 지원,
OT/통신 호환 또는 저장 후 재실행 완료로 선언하지 않는다. 레포트·종료·새 실행
재로드의 통합 테스트는 해당 소비자 경계를 정리한 다음 단계에서 진행한다.

## 사용자 통합 검증 보고 / E 한 화면 키보드 구현

사용자는 D1b 테스트와 레포트 저장·재로드·OT 경로 검증에 이상이 없다고 보고했다.
첨부된 카드 화면도 이름 재표시의 대표 증거다. 저장 파일/재실행 방식/OT 소비자
전체의 세부 결과는 제공되지 않았으므로 이 보고를 모든 통신·오류 교정 경로의
완료 증거로 확장하지 않는다. 앞서 찾은 OT 길이 제한 등 정적 위험은 별도 점검
대상으로 남긴다. 이번 변경은 키보드 표면과 입력/커서 배치에 한정한다.

사용자의 E 단계 선택:

- 골드 참조는 기호가 없으며 빈 칸도 공백 입력 셀이라고 확인했다.
- 구현이 간단하고 목표와 일치하는 쪽을 에이전트에게 선택하도록 요청했다.
- 골드식 자음/모음 한 화면 + 정정/결정을 채택한다. 영문·숫자 페이지나 기호
  페이지를 추가하지 않는다. 선택 가능한 빈 칸 8개는 모두 공백($0bff)을 입력한다.
  그룹 사이의 구분용 간격은 원작처럼 커서가 건너뛴다.
- 대사 및 기존 YOUR NAME? 제목 문자열은 변경하지 않는다. 제목 번역은 기존의
  사용자 직접 편집/사전 승인 원칙을 유지한다.

E 구현:

- engine/menus/hangul_player_keyboard.asm을 같은 Naming Screen 섹션에 추가했다.
  주인공만 새 그리기/키 판독/커서 분기로 들어가며 다른 이름 입력은 기존 경로다.
- HangulPlayer_Layout은 gold/data/text/name_input_chars.asm의 133바이트와 같다.
  그림의 18타일 + 행간 이동을 7행 복사해 자모 4행 및 정정/결정 3행을 배치한다.
  y=7의 원래 테두리 구분선을 보존하고 마지막 출력은 y=17 안에 둔다.
- 커서는 12열, 자모 4행 + 명령 1행이다. 골드의 불균등 X 간격 및 명령 커서
  오프셋/작은·큰 커서 프레임을 사용한다. START는 결정으로, B는 정정으로 연결한다.

화면 또는 커서가 어긋나면 선택한 행/열과 실제 입력 결과를 함께 기록한다.
